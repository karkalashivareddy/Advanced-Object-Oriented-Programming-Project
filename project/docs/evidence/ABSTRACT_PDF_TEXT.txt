Abstract LifeLink is a blood bank coordination platform that unifies donor registration, donation screening, blood-unit inventory, hospital emergency requests, allocation, reservation, dispatch, notification, audit, and analytics. It addresses the inconsistency and poor traceability of manual blood distribution, where a unit can be promised twice, an unscreened donation can be released, expired stock can be issued, and one organization can see another organization’s data. The backend is a Java 21 / Spring Boot modular monolith; a React/TypeScript single-page application consumes its REST API and authenticated STOMP notifications. Domain entities with guarded transitions, database constraints, row locks, optimistic versioning, deterministic lock ordering, and persisted idempotency keys protect critical workflows. Audit records and a notification-only outbox preserve decisions and durable notification intents in the same transaction. The expected outcome is a testable platform that prevents double reservation, blocks illegal transitions, provides inventory alerts and scoped analytics, and demonstrates encapsulation, abstraction, inheritance, polymorphism, interfaces, exception handling, collections and generics, and strategy/specification/ repository patterns in real Java classes. The local runtime uses Dockerized PostgreSQL 16 on a Windows development host; Linux-based container images are runtime packaging, not the application’s programming language or implementation platform. Problem Statement Manual or spreadsheet-based blood distribution separates donors, blood banks, inventory staff, hospitals, and medical staff without one source of truth. Availability may be checked before a unit is locked, allowing double reservation; a donation can be approved without a recorded screening; expired or quarantined units can be issued; a request can be fulfilled without a traceable reservation and dispatch; one organization can see another organization’s stock or donor data; and no audit trail explains who changed a unit’s state. At runtime the Spring Boot JVM uses request and scheduled threads, TCP sockets, filesystem-backed configuration/migrations/ logs, timers, and database locks. These are relevant operating-system and runtime mechanisms, but they support consistency; they do not replace domain invariants, database constraints, server-side authorization, or transactional boundaries. 4. Proposed System LifeLink is implemented as a modular monolith with twelve business packages under com.lifelink.<module>. The Java backend owns all domain rules, persistence, authorization, validation, transaction management, aggregation, and API responses. The React/TypeScript single-page application is a separate static client: it presents forms, tables, charts, and role- aware navigation, calls /api/v1 over REST, and opens an authenticated SockJS/STOMP connection for notification-cache invalidation. It does not connect to the database and does not enforce critical business rules. The REST inbox remains the authoritative notification path; STOMP only invalidates React Query caches so the badge and open inbox refresh promptly. The browser falls back to REST polling when a socket cannot connect, and anonymous visitors never open a socket. LIFELINK · 5. Database and Data Management • Flyway V1–V5 create the core schema, operational tables, dispatch idempotency, integrity constraints and persistent token version; Hibernate ddl-auto=validate checks the mapping. • JPA entities use private state, explicit relationships, @Version optimistic locking, and PESSIMISTIC_WRITE queries for contended units and requests. • Unique indexes and a sparse one-active-reservation-per-unit slot prevent duplicate public identifiers and double reservation. • Critical writes use persisted idempotency records with request fingerprints; replay returns the original result, while a divergent payload is rejected. • audit_events is append-only in practice; outbox_events stores notification intents only. No tamper-evident audit or generic domain-event log is claimed. • Many collection endpoints are paginated; several array-returning endpoints are not, including donors, donations, emergency requests, reservations, dispatches, organization members, and inventory movements. Tenant-scoped queries and validated X-Organization-Id still prevent cross-organization disclosure. 11. Security and Access Control • BCrypt password hashing, JWT access tokens with jti and persistent token_version, and rotating refresh tokens with replay detection. • Role-based access plus fine-grained permissions are enforced in Java services and controllers; UI hiding is never treated as authorization. • Every protected request validates the bearer token and, where applicable, the X-Organization-Id header; platform admins may deliberately work unscoped. LIFELINK · • Bean Validation and defensive service guards reject blank reasons, null priorities, invalid adjustment deltas and malformed identifiers before persistence. • STOMP CONNECT requires a bearer JWT, SUBSCRIBE is limited to the caller’s own queue, and client SEND frames have no message-mapping handlers. • Secrets are supplied through environment variables; CORS is limited to local loopback origins; demo accounts are development fixtures only. 12. Expected Outcomes and Verification The implemented platform demonstrates a continuous chain: screened donations create quarantined units; authorized staff release them; hospitals raise requests; advisory allocation suggests compatible units; confirmed allocations create idempotent reservations; and dispatches move through departure and delivery with audit records and notifications. Inventory alerts, scoped analytics, and responsive role-aware pages are backed by Java API responses rather than fabricated data.
