1. Abstract



LifeLink is a blood bank coordination platform that unifies donor registration, donation screening, blood-
unit inventory, hospital emergency requests, allocation, reservation, dispatch, notification, audit, and analytics. It
addresses the inconsistency and poor traceability of manual blood distribution, where a unit can be promised twice, an
unscreened donation can be released, expired stock can be issued, and one organization can see another organization's
data. The system models the supply chain as guarded Java domain objects whose state transitions enforce real
invariants. A modular Spring Boot REST service and React/TypeScript single-page application share one PostgreSQL
database; Flyway migrations, scoped authorization, and database constraints complement object-
level checks.

The local runtime uses Dockerized PostgreSQL 16 on a Windows host; Linux containers are runtime
packaging, not the application language. Pessimistic row locks, optimistic versioning, ordered locking, and persisted
idempotency keys prevent double reservation and duplicate dispatch. Audit events and a notification-only outbox
preserve decisions and durable notification intents. The expected outcome is a testable platform that blocks illegal transitions,
provides inventory alerts and analytics, and demonstrates encapsulation, abstraction, inheritance, polymorphism,
SOLID, strategy/specification/repository patterns, generics, exceptions, and concurrency in real Java classes.


2. Problem Statement
Manual or spreadsheet-based blood distribution separates donors, blood banks, inventory staff, hospitals, and medical
staff without a single source of truth. Availability may be checked before a unit is locked, allowing double reservation;
a donation can be approved without a recorded screening; expired or quarantined units can be issued; a request can be
fulfilled without a traceable reservation and dispatch; a user of one organization can see another organization's stock or
donor data; and no audit trail explains who changed a unit's state. These are consistency, concurrency, authorization,
and traceability problems. A Java/Spring Boot solution must enforce invariants in the object model and database, serialize
contended writes, scope every request to an organization, and record decisions durably.

3. Objectives



Model the donation-to-dispatch workflow as encapsulated aggregates with guarded state transitions and validated
invariants.

Provide a REST API and responsive SPA for donor, bank, inventory, hospital, medical, and administrator journeys
with server-side role and tenant authorization.

Prevent double reservation, duplicate dispatch, and illegal release using row locks, optimistic versioning, deterministic
lock ordering, and persisted idempotency keys.

Preserve end-to-end auditability and durable notifications through append-only audit events and a transactional outbox,
verified by automated tests.

4. Proposed Methodology




Implement a modular monolith in Java 21 and Spring Boot with a React/TypeScript single-page application. Define
JPA entities and Flyway migrations for organizations, users, donations, units, requests, reservations, dispatches, audit
events, and the outbox. Expose REST endpoints with DTO validation, bearer-token authentication, and organization
scoping; services orchestrate workflows while domain methods reject illegal transitions.

Repository row locks and @Version guard contended writes, deterministic lock order avoids deadlocks, and
idempotency records deduplicate replayed commands. The frontend consumes real APIs with token refresh and an
organization scope selector. Verify the result with domain, integration, PostgreSQL concurrency, frontend component,
Playwright browser E2E, and Compose health probes.

8. Expected Outcome


LifeLink will demonstrate a working end-to-end blood supply workflow: screened donations create quarantined units,
authorized staff release them, hospitals raise requests, suggestions rank compatible units, confirmations create
idempotent reservations, and dispatches move through depart and deliver with audit events and notifications. It
prevents double reservation, unauthorized cross-tenant access, and illegal state transitions.

The expected evidence includes inventory alerts, scoped analytics, a responsive verified UI, 119 backend tests, 39
frontend tests, 18 Playwright browser passes, PostgreSQL concurrency checks, and live STOMP and Compose health
probes.
